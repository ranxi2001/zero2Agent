# pi-ai：统一 Provider 的边界

Agent 若直接绑定一家模型 SDK，起步简单，却会把消息格式、流式事件、工具调用和错误处理散落到业务代码。Pi 的 `pi-ai` 选择建立统一适配层，让上层 runtime 面向稳定语义，而不是某一家 SDK。

> 本文基于 2026-08-24 的官方仓库 commit `a470b121`。Provider 与模型目录会更新，不在正文维护易过期的数量和版本表。

## 统一的是什么

适配层通常需要统一：

- 用户、助手与工具结果消息；
- 工具 schema 与 tool call；
- 文本、thinking 和工具参数的流式增量；
- stop reason、错误与 token usage；
- 模型能力和上下文限制等元数据。

上层 Agent Loop 因此可以使用同一套控制流：接收事件、执行工具、追加结果、继续请求模型。

## 统一不代表行为相同

不同 Provider 对并行工具、推理内容、缓存、多模态和错误重试的语义并不完全一致。切换模型后，即使代码没有变化，也可能出现：

- 工具参数质量和调用轮数改变；
- stop reason 或错误形态改变；
- 上下文限制与计费方式不同；
- 某项能力存在，但另一个 Provider 无法等价表达。

因此，Provider 应是运行时配置，但能力差异必须通过测试暴露，不能只靠接口类型掩盖。

## 一个可复现的比较方法

选择同一项只读任务，在两个模型上记录：

1. 是否选对工具；
2. 参数是否通过 schema 校验；
3. 完成任务用了几轮模型请求；
4. 工具失败后能否恢复；
5. 总 token、延迟和最终验证结果。

这比宣称“支持多少家 Provider”更有工程价值。模型目录增加很快，任务成功率和失败恢复才是你的系统真正依赖的契约。

## 何时值得使用统一层

适合：需要多模型切换、A/B 测试、统一日志或把模型选择留给部署配置。

不适合：业务深度依赖某家独有 API，且统一层只能大量透传厂商字段。此时应明确承认绑定，而不是制造“完全可移植”的假象。

## 小结

`pi-ai` 的价值不是消灭差异，而是把差异关在可识别的边界里。统一接口负责稳定控制流，能力探测和回归测试负责揭示抽象泄漏。
