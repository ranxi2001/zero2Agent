# 先写 Skill：什么时候才需要 MCP

看到一个重复任务就接 MCP，常常会把“模型不知道流程”误诊成“模型缺少协议”。MCP 解决的是工具与资源的标准化互操作，不负责替你写清业务步骤。

## 先判断缺的是什么

- 模型已有 `read`、`bash` 等能力，只是不知道团队流程：写 **Skill**。
- Pi 缺少一个受控的本地能力：写 **Extension Tool**。
- 已有 MCP Server，需要被 Pi、Claude Code 等多个宿主复用：接 **MCP**。
- 需要标准化发现远端工具、资源或 Prompt：接 **MCP**。

例如“发布前依次检查版本、测试、diff 和回滚条件”是流程知识，优先 Skill。只有 Jira、数据库或浏览器能力已经以 MCP Server 提供，或确实需要跨宿主共享时，MCP 才带来明显收益。

## MCP 的真实成本

引入 MCP 后，多了至少四类工程问题：

1. **发现成本**：工具 schema 怎样进入上下文，何时懒加载。
2. **选择成本**：模型能否先找到正确工具，再生成正确参数。
3. **生命周期**：连接、重连、认证、超时和进程退出如何处理。
4. **安全边界**：谁批准高风险工具，输出如何裁剪，凭据存在哪里。

不要引用缺少实验条件的“节省多少 token”数字。若上下文成本是关键问题，应在同一模型、同一工具集、同一任务上比较 direct tools 与 proxy/discovery 方案，记录首轮 token、调用轮数、成功率和延迟。

## 最小验收清单

- 工具发现失败时有可诊断错误；
- 高风险工具不会默认静默执行；
- 输出过大时明确截断，并保留定位原始结果的方法；
- OAuth、Token 和日志不会进入会话或仓库；
- Server 崩溃、超时和 schema 变化都有测试；
- 移除 MCP 后，核心业务流程仍有清晰说明。

## 结论

**重复流程优先 Skill，运行时能力才用 Extension，跨宿主协议互操作再用 MCP。** 这个顺序不是反对 MCP，而是避免在知识问题上增加一个分布式系统。
