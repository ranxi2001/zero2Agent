# 安全边界：信任、权限与隔离

Agent 说“我不会执行危险命令”，不是安全保证；项目显示“已信任”，也不代表代码被关进沙箱。安全设计首先要区分三类边界。

## 三类边界不能互相替代

### 项目 trust

项目被信任后，Pi 才会加载项目级 Skill、Extension、Package 和设置。它降低了陌生仓库自动执行本地资源的风险，但不限制已加载代码能够访问什么。

### 工具审批与策略

Extension 可以在工具调用前检查参数、要求确认或拒绝动作；MCP 集成也可为特定工具增加审批。这类控制适合表达“允许读、不允许发布”，但实现本身仍运行在 Pi 进程里。

### 操作系统隔离

容器、虚拟机、低权限账号和网络策略决定最坏情况下能损害什么。它们才是文件系统、进程、网络和凭据的强边界。

## Pi 的实际权限

Pi、Extension 以及 Skill 引导执行的脚本，原则上都继承当前进程权限。安装第三方 Package 相当于信任其最高风险组成部分，而不是只看市场描述。

首次运行未知资源时：

- 使用临时工作区和低权限账号；
- 不注入生产 Token；
- 限制可写挂载、网络、CPU、内存和进程数；
- 检查安装脚本、`exec`/`spawn`、网络请求与主目录访问；
- 固定版本或 commit，并准备卸载与回滚。

## 容器也会配置错误

“放进 Docker”并不自动安全。常见失误包括：以 root 运行、挂载整个主目录、透传 SSH/云凭据、开放宿主 Docker socket、默认允许任意外网访问。

一个更可靠的检查顺序是：

1. Agent 能看到哪些文件？
2. 哪些目录可写？
3. 能访问哪些网络目标？
4. 凭据以什么方式进入？
5. 谁批准删除、发布和外部写操作？
6. 失败后如何审计和回滚？

## 结论

Project trust 解决“是否加载项目资源”，审批解决“是否执行某次动作”，沙箱解决“动作最坏能影响哪里”。三者缺一不可，也不能用 Prompt 替代。
