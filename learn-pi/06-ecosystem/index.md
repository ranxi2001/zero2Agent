# 生态使用：发现不等于信任

Pi 的可扩展性让社区很容易分享 Skill、Extension 和整包配置，但“能安装”只说明可发现，不说明安全、兼容或值得维护。

## 两个发现入口

优先从 [Pi Package 市场](https://pi.dev/packages) 找包；需要更广的社区目录时，再看 [awesome-pi-agent](https://github.com/qualisero/awesome-pi-agent)。二者都不能替代源码审计。

## 跨框架 Skill 为什么可行

Pi 使用 Agent Skills 标准，并能从配置的共享目录发现 Skill。可移植的核心是 `SKILL.md` 的渐进披露结构、相对资源和共同约定，而不是“JSON 纯函数工具协议”。

兼容仍有边界：

- 不同宿主拥有的工具和权限不同；
- project trust、目录发现和命令入口不同；
- Skill 中的脚本依赖本机运行时；
- 同名资源、版本和加载优先级需要实测。

所以“同一 Skill 可被多个 Harness 发现”不等于“行为完全一致”。

## 安装前的十分钟审计

1. 查看作者、源码、许可证和最近维护时间；
2. 固定版本或 commit；
3. 区分包内的 Skill、Extension、模板和主题；
4. 检查依赖、安装脚本、shell、网络和动态代码加载；
5. 搜索 SSH、云凭据、环境变量、浏览器配置和主目录访问；
6. 在无生产密钥的临时仓库试运行；
7. 验证安装、更新、禁用与卸载路径。

## 何时应该 Fork

当你必须长期依赖某个社区包，而上游维护节奏、权限范围或接口稳定性不符合要求时，Fork 是一种供应链治理方式。但 Fork 会把安全更新、兼容测试和文档维护转移给你，不能只复制代码后停止跟踪。

## 结论

社区列表用于发现，官方文档用于理解机制，源码和隔离环境用于建立信任。生态越繁荣，越需要清晰的版本、权限和退出策略。
