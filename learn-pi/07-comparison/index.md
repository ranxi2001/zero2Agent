# Pi、Claude Code 与 DSH：按约束选 Harness

选 Harness 不是选功能最多的产品，而是选择谁负责模型适配、会话事实、安全策略和扩展执行。动态 star 数和宣传口号都不适合当决策依据。

> Pi 行为按 2026-08-24 官方 commit `a470b121` 核验；其他 Harness 迭代同样迅速，正式选型前应重新验证当前版本。

## 可验证的决策矩阵

| 问题 | Pi | Claude Code | DeepSeek Harness |
| --- | --- | --- | --- |
| 主要交互 | TUI，也支持 print/JSON、RPC、SDK | 产品化 CLI 与编辑器入口 | 可组合运行时与多宿主入口 |
| 模型策略 | `pi-ai` 面向多 Provider | 围绕 Claude 深度集成 | 通过适配与插件组合 |
| 会话 | 原生持久化、恢复、树形分支与 compaction | 原生会话能力 | 以运行时日志和插件管理 |
| 定制 | Skill、Extension、Package | Skill、Hook、MCP 等产品接口 | 插件化控制面 |
| 安全重点 | project trust + 外部隔离；扩展需自审 | 产品内权限与沙箱能力 | 策略、审批与沙箱组合 |
| 控制流改造成本 | Extension API 范围内较低，改核心需维护 Fork | 受产品接口约束 | 可组合性强，但维护复杂度更高 |

这不是评分表。每一格都应通过你自己的任务验证，而不是从表格直接推出“最佳”。

## 选型前做同一组实验

在候选 Harness 上运行同一仓库任务：

1. 读取项目规则并给出计划；
2. 修改两个文件并运行测试；
3. 在工具执行中插入新指令；
4. 中止后恢复会话；
5. 分支出另一种实现；
6. 触发一次危险写操作并观察拦截；
7. 导出日志，确认能追踪模型请求、工具结果和验证证据。

记录任务成功率、人工确认次数、恢复质量、token、延迟和最坏权限范围。这样得到的是适合你团队的证据，而不是通用排名。

## 三类典型约束

- 已有隔离平台、需要多模型和高定制：Pi 值得优先验证。
- 希望权限与产品体验开箱即用、主要使用 Claude：优先验证 Claude Code。
- 研究控制平面、策略编排或可替换 Loop：优先验证 DSH。

工具可以通过 MCP 等协议复用，Skill 也可能跨宿主共享；但会话语义、上下文构造、审批和控制流仍属于各自 Harness。迁移时最容易被低估的是这部分。

## 结论

不要问“哪个最好”，要问：事实源在哪里、失败能否恢复、危险动作由谁阻止、扩展代码在哪个权限域执行、升级后谁负责兼容。能用实验回答这些问题，选型才算开始。
